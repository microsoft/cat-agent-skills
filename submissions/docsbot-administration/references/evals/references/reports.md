# Review a report or compare tests

Inspect advertised metadata for `list_eval_runs` and `get_eval_run` before choosing a saved-report workflow. If the needed tools are absent, review results the user supplies or diagnose normal question/conversation history through the response-quality workflow. Do not invent runs, scores, a report link, or an automated follow-up test.

1. When run-read tools are advertised, read the selected run and requested baseline by ID; otherwise use only the results the user supplied. Respect the user's selected comparison; do not silently substitute the latest run. Read the question set and captured settings where relevant.
2. Establish completion and scored/skipped/error counts before interpreting quality. Missing scores and operational failures are not zero-quality answers. Report their separate impact on confidence.
3. Pair results by stable case ID. Compare only cases with the same question, expected answer, and required actions and finite scores in both runs. New, removed, edited, and skipped cases are not valid score-change evidence. Mention matched sample size and changes to model, prompt channel, knowledge, scoring, or enabled actions that limit causal claims. Percentage score differences are percentage points.
4. Explain overall quality in plain language, then focus on important regressions and failures. Inspect actual vs expected answers, judge rationale, grounding, semantic similarity, and required action failures. A high average can hide a critical failure. A terse answer is not automatically worse, and semantic similarity is not proof of correctness.
5. Separate source gaps, incorrect test expectations, instruction problems, missing/failed tools, retrieval issues, and run infrastructure errors. Verify claims against sources and current configuration. Never invent retrieved evidence, latency, cost, or a causal explanation absent from the report.
6. Recommend the smallest appropriate fix. For instruction changes load instructions.md; for inaccurate cases load questions.md; for retrieval investigation use the response-quality skill. Review concrete changes before applying unless already explicitly authorized. After an authorized fix, use the same questions for a manual follow-up check and preserve the baseline. Offer a saved-set run only if its required named tools are advertised and the user authorizes it.

When advertised, use `list_eval_runs` and `get_eval_run` for test runs and reports. Inspect the live list schema and pagination limits; use a known run ID when older reports are not listed. Completion of a run and completion of a remediation are separate outcomes.
