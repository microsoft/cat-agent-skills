# Build useful questions

Before reading or saving a set, inspect advertised metadata for `list_eval_sets`, `get_eval_set`, and the specific write tool needed. Use only returned named tools and schemas. If set tools are absent, follow the drafting and evidence steps below using available `get_bot`, `list_questions`, and source reads, keep the proposal in this conversation, and do not claim it was saved or offer an unavailable automated run.

1. Read the bot and, when set-read tools are advertised, the selected question set. Preserve existing case IDs, categories, notes, required actions, and scoring settings. When advertised, use `add_eval_question` for a single addition; `update_eval_set` replaces cases, so fresh-read before composing the entire payload.
2. Inspect relevant indexed sources. For history-based tasks, inspect a bounded sample of recurring, poorly rated, unanswered, or escalated conversations. Remove names, account identifiers, secrets, and other personal details. A previous bot answer is evidence of behavior, not an authoritative expected answer.
3. Cover realistic common questions, known failures, ambiguous/edge cases, useful paraphrases, and action requirements. Prefer a small useful first set over filler. Avoid near-duplicates and questions the knowledge cannot answer reliably.
4. Write a natural customer question, a concise source-backed expected answer, and optional evidence notes. Expected answers should express the necessary meaning, not require exact phrasing. Where policy is missing, surface the gap or test appropriate uncertainty rather than inventing facts.
5. Use the supported categories: common, known_failure, edge_case, action_needed, paraphrase. Preserve other tags. Require only actions actually enabled for the tested channel, using catalog/tool IDs from current bot configuration. Do not add action assertions to every case merely to raise coverage.
6. Present additions/edits for review with question, expected behavior, category, and any required action. Clarify substantive unknowns. On authorization and only when the needed tool is advertised, save through `create_eval_set`, `add_eval_question`, or `update_eval_set` as appropriate, then read back the exact set. Do not start a run automatically unless authorized.

When advertised, use `list_eval_sets` and `get_eval_set` to inspect existing sets. Inspect the advertised schemas for `create_eval_set`, `update_eval_set`, and `add_eval_question` before writes. Confirm supported promptTarget values and case limits from advertised schemas; the described Evals workflow targets agent and helpscout, with up to 250 cases. Voice instruction work is separate; keep IDs when editing and avoid silently dropping cases at the limit.
