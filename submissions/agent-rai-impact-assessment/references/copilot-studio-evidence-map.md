# Copilot Studio evidence map

Use this map when the assessed agent is built in Microsoft Copilot Studio. It tells you which configuration and runtime evidence to request for each lens. Entries describe where evidence usually lives, not guaranteed product behavior: feature names, settings, and defaults change, so confirm each item against the actual agent configuration and current Microsoft Learn documentation before treating it as a control.

| Lens | Where to look in Copilot Studio | What to record |
| --- | --- | --- |
| People and benefits | Agent description and instructions; the channels it is published to (Teams, Microsoft 365 Copilot, web, custom); who the agent is shared with; the environment it lives in. | Intended users versus everyone who can actually reach it; whether non-users' records are read or changed. |
| Action authority | Tools and actions: connectors, Power Automate or agent flows, prompts, MCP servers, REST APIs; each tool's authentication mode (end-user credentials versus maker- or connection-supplied credentials); input parameters the model controls; generative orchestration settings; tools blocked or allowed by the tenant's data policies. | For each consequential tool: effective identity, resource and parameter scope, whether the restriction is enforced in the tool or downstream system rather than in the instructions. |
| Effective human control | Whether the agent asks the user to confirm inputs before a tool runs (inspect the tool's settings and a real transcript rather than assuming a setting exists); approval steps inside agent flows, including multistage and AI approvals; what the confirmation or approval card actually shows; topic designs that pause for input. | Whether approval is bound to the exact parameters, what the approver sees, and what happens if the approver is absent or the flow retries. |
| Retrieval and untrusted content | Knowledge sources: SharePoint, OneDrive, Dataverse, websites, uploaded files, search indexes; whether retrieved content can reach a tool call; connected agents that return content; the content moderation level set per generative answers node (Lowest to Highest, default High). | Which sources are writable by people outside the owning team; evidence of injection testing with synthetic fixtures; tool-side restrictions independent of retrieved text. |
| State and retries | Flow run history and retry settings; connector timeout behavior; whether tools are idempotent; multiple channels or sessions acting on the same record. | Duplicate or partial-action evidence from run history; recovery steps and who performs them. |
| Privacy and memory | Knowledge source permissions and whether user-level permissions are respected at query time; conversation transcript storage and retention in the environment; analytics data; any memory or variables persisted across sessions; connected-agent context sharing. | Who can read transcripts and logs; retention period; whether derived data keeps the source permissions; data residency of the environment. |
| Reliability and grounding | Grounding and citation behavior in test transcripts; knowledge source freshness and ownership; fallback and escalation topics; supported languages configured on the agent. | Citation support rather than citation presence; behavior when sources conflict or a tool fails; handoff path to a human. |
| Fairness and inclusion | Languages enabled; channel accessibility; test coverage across user groups and request types; escalation routes by channel. | Evaluation slices actually run, their sample sizes, and groups with no coverage. |
| Transparency and recourse | Welcome and disclosure messaging; how the agent reports an action it took; escalation to a live agent or named owner; correction route for affected non-users. | Whether a person can tell what was done on their behalf and whom to contact. |
| Multi-agent delegation | Connected or child agents, their owners, tools, and authentication; what context is passed; whether the parent's restrictions apply to the child. | Identity and scope at each hop; who owns the combined outcome. |
| Operational change | Solutions and environment strategy; publishing history; data policies (formerly data loss prevention) configured in the Power Platform admin center and enforced for all agents; audit logging through Microsoft Purview; analytics dashboards; who can edit and publish the agent. | Versioned baseline, change approval route, monitoring signals in use, and the mechanism for stopping new actions. |

Evidence requests that are usually enough for a first pass: the exported solution or a screenshot set of instructions, knowledge sources, tools and their authentication settings; two test transcripts per consequential action, one normal and one failure; the sharing and publishing settings; and any analytics or run-history export covering a representative period.
