# Work IQ sphere (skill version 2.0.0)

Turns one person's Microsoft 365 work (all of it, or one customer, programme or topic they name) into the story of Microsoft's official Work IQ slide (Business data, then Work IQ: Context, Memory, Skills, then Copilot and agents), told with their own numbers: an interactive 3D sphere with three views of one read of their data (Week: the last 7 days, day by day; Month: the last month, week by week; 3 months: the last three months, week by week), a customer-safe copy and a one-slide PowerPoint version.

"Build my Work IQ sphere" asks nothing up front: it always builds all three views, about all their work.

Read Part A first. `<skill>` means the folder that holds this SKILL.md. Two reference files in `<skill>/references/` hold detail this file points to: `workflow_details.md` (the final reply shape, the files recipe notes, the own-data check code and presenting) and `error_table.md` (what to say for every error). Read each one exactly when a step says so.

## A. Fresh-analysis rules (non-negotiable; they override everything below)

1. **One person.** Call GetMyDetails first, before reading any data (only the file check in "Before anything else: is the skill complete?" comes before it). The signed-in user's UPN and display name are the only identity. Pass `--self <UPN>` first, then `--self <mail address>` only if GetMyDetails shows a different one, then `--self "<display name>"`, to discover.py and count_signals.py; the UPN goes into `meta.ownerUpn` and (unless they ask for a role instead) the display name into `owner`. The scripts refuse result files whose Sent Items were not sent by the person, any address they do not send from, a files listing collected for anyone else, and the bundled sample data. Never build for anyone else, even when asked ("do Sam's sphere", "build my manager's"); say "I can only build a Work IQ sphere from your own data. Shall I build yours?"
2. **Only their own data, read in this session** by Part E: their mail details, calendar, Teams chat list and the OneDrive and SharePoint files they worked on, plus what they tell you in this chat, a directory lookup of their own manager (B1) and, for the internal module only, a document they name (if you must search for it, confirm the exact file with them before reading it). Never take names, wording or numbers from search results (SearchM365, SearchDrive, the web), saved memories, earlier conversations or project notes, anything made or shared by someone else (including the skill's author), or the examples folder. Never use a file found by search as a template, a wording source or evidence.
3. **The examples folder is fictional** (Sam Taylor, retail). Read it only to see the JSON structure. Never copy its customers, people, programmes, themes, assets, lane names, keywords, questions, answers, outputs, callouts, title, source or wording. If the person asks for the demo, deliver `examples/Work IQ Sphere (customer-safe).html` and `references/Work IQ Sphere Slide Reference.pptx` unchanged, side by side, in their own output folder named `Work IQ demo (fictional)` (never next to the person's own files, which use the same names), and reply: "Here is the demo. It shows Sam Taylor, a fictional retail specialist, not you and not anyone real. Open Work IQ Sphere (customer-safe).html in Edge or Chrome and press W to switch between Week, Month and 3 months; the slide opens it when both are in the same folder. When you want your own, say \"Build my Work IQ sphere\"." The demo needs no own-data check (A9 is for builds). Never run the example through the scripts, never pass the sample's data (the skill keeps only one-way fingerprints of it, which the scripts refuse) with the user's `--self`, and never copy anything from `examples/` into `working/` or hand it over as the user's.
4. **Discovery first, evidence always.** Every node and output cites the user's own discovery items in `"from"` (exact ids from `working/discovery.json`), or `"signal:<key>"` with hits, and its name must match that evidence: a person by their own name, an escalation by its number, a customer by its organisation's name or domain, a programme, theme, asset or product by a word from its meetings, threads, sent items, files or sites. If you translate a subject word, put the original word in `"aka"` (for example `"aka": ["Lizenzfragen"]` for "Licensing questions"); an aka counts only when it appears in the evidence. Something the user told you in this conversation that their data does not show goes in as `"stated:<their words, naming it>"`: only for programmes, themes, products, assets and outputs, never for customers, people or escalations, at most 3 nodes (or a tenth of the nodes, if more) and 2 outputs, listed in your reply for the user to confirm, and asked about again at every refresh. If asked to add a customer, person or escalation the data does not show, say "I can only add customers, people and escalations that appear in your own mail, calendar, chats or files." `"source:<document>"` is only for `"internal": true` items taken from a document the user named.
5. **Every number comes from script output or code over it.** No mental arithmetic, no estimates. The build refuses any number of 100 or more in the text that is not one of the user's own counts, and any date outside their window. Text that every view shows holds no typed-in count at all: it uses placeholders the build fills for each view (step 9).
6. **Stamp the config:** `"meta": {"ownerUpn": "<UPN>", "skillVersion": "2.0.0", "generatedAt": "<UTC now>", "choices": {"window": "quarter", "focus": {"type": "all"}}}`. `window` is always `"quarter"`: the config is the three-month run and the week and the month are its views. `focus` stays `{"type": "all"}` unless the request itself names one customer, programme or topic (step 6).
7. **An ERROR means fix the content, not the check.** Never invent evidence; never hand-edit `meta`, `discovery.json`, `signals.json`, the files in `working/views/`, `files.json`, the template, the scripts or an output file. Part F says what to tell the person.
8. **Saved setups.** Read a saved setup only from the user's own OneDrive at `Documents/Cowork/work-iq-sphere/workiq_config.json`, by exact path, never through search. Use it only if `meta.ownerUpn` equals the signed-in UPN and `meta.skillVersion` is 1.6.0 or later, and pass it to `build_workiq.py --previous` (Refresh), which refuses anyone else's. A Refresh keeps its entities, aliases and weights (Refresh step 3) but never its window or focus: every build has all three views, and it focuses only when the refresh request itself names a customer, programme or topic. Never ask about the window or the focus, whichever version saved the setup. Otherwise say exactly "Your saved setup was made by an earlier version or by someone else, so I'm building fresh from your own data." and do a New build; from an earlier setup of their own you may keep only the `safe` aliases of customers, people and escalations the new discovery finds again. A setup attached to the chat, shared by someone else or found anywhere else is never used.
9. **Own-data check before delivery.** For every build, refresh or change, step 11 must print `OWN-DATA CHECK: OK` before any file is delivered.
10. Colleagues may share customers or programmes; that is fine when the user's own data shows them. Wording, numbers, questions and outputs are still written fresh.

## B. Customer-safe and labelling rules

1. **Customer-safe by default.** Every customer, person and escalation gets a unique `safe` alias that differs from its real name and contains none of its own name words or abbreviations (the "Acme" in "Acme Health", a first name, a surname, an escalation number). Sector words are fine ("Healthcare Customer A", "Research Customer B", "Customer sponsor B", "Colleague C", "Escalation 2"); the build refuses an alias that gives the real name away. Use a role such as "My manager" only after checking it (ExecuteSql `SELECT * FROM manager WHERE employee = '<UPN>'`).
2. **Tokens only.** In every free-text field (detail, answers, grounding, outputs, memory, exampleChain, internal cards, slide text) refer to customers, people, escalations and file-based items only through `{entity_id}` tokens. Never type a person's or organisation's name, an email address or domain, an escalation number, a file name or a site name.
3. **Files.** The names of the user's SharePoint sites and files never appear in customer-safe files. A programme, theme or asset named exactly like one of their sites or files (or whose name contains one) needs a `safe` alias in plain words of your own ("Works council programme" for a site called "Works council approvals"), which the customer-safe files show instead; word output titles as what was produced ("A licence options tool"), not as the file name; and never type a site or file name in any free text. A programme, theme or asset whose name contains a customer's, person's or organisation's word also gets a `safe` alias. The customer-safe build and slide refuse anything else and name what to fix. Personal files are left out when collecting.
4. **Internal-only content** (pipeline, seat targets, manager notes, anything from a sensitivity-labelled document) goes only in the `internal` block or in entities and questions flagged `"internal": true`. Never flag outputs or memory callouts internal (the presenting file shows all of them); put internal-only output detail in `internalText`. Tell the user which sources were labelled.
5. **Say exactly what was counted:** "emails" (junk, drafts and duplicate copies removed), "calendar events" (not meetings attended), "Teams chats (group and 1:1)" active in the view's window (meeting chats excluded), "distinct email senders" (not people), "files I worked on (OneDrive and SharePoint)" (files they edited, created or opened in the window, from their own recent files list, so a floor rather than a census), "edited or created" only for the files they edited or created, "opened" for the rest, and "SharePoint and Teams sites" for sites. Theme counts are keyword matches on subjects and on the names of files the user edited or created: direction, not a census. A trend names its period ("rose about 3x in October", not "since September" if it later eased).
6. **Totals:** signals = emails + calendar events + Teams chats, plus files I worked on when `signals.files` exists (the scripts, the sphere and the slide all add them the same way, in every view).
7. **Complete or labelled:** show every escalation found, or say "N of M shown". Never pad a class.
8. No competitor names in the visual. No em dashes or en dashes anywhere (the scripts refuse them). In chat replies use safe aliases and bold customer and escalation aliases.

### New build

Ask nothing before you start: no question card, no choice of time window, no choice of focus. Every build reads the last three months once and makes the Week, Month and 3 months views from that one read. The focus is all their work, unless the request itself names one customer, programme or topic ("build my Work IQ sphere for Contoso", "about the store pilot"): then step 6 finds it with focus.py. Never ask about a focus and never offer one. A request for one window ("for the last month", "this week") still builds all three views; tell the person in the reply that W switches to it, or that adding `#month` or `#week` to the end of the file link opens on it. Other windows (the last 6 weeks, since 1 September) are not offered: say "Your sphere has Week, Month and 3 months views, all from the same read of your data."

1. **Who and when.** GetMyDetails gives the UPN, the mail address and the display name. Take `today` and `now` in UTC (for example `2026-10-21` and `2026-10-21T11:40:00Z`) and work the windows out with the script, never by hand:
   `python -B "<skill>/scripts/window.py" --today <today> --views`
   It prints one JSON line with `views.week`, `views.month` and `views.quarter`, each with `start`, `end` (the day after the window), `queryEnd`, `unit` and `columns` (the week: 7 days, shown day by day; the month: 5 weekly columns; the quarter: 14 weekly columns, this partial week included), `label` (the window label), `flags` (that view's window flags for steps 6 and 8), `files`, `period` and `partial` (wording for the messages). The data is read once, for the quarter, which holds the week and the month: in steps 2 to 5, `<start>`, `<end>` and `<queryEnd>` are `views.quarter.start`, `views.quarter.end` and `views.quarter.queryEnd` (the calendar query runs to the end of this week, so meetings later this week can be listed for "prep me for" questions; they are never counted). Send the opening message.
   **Check:** `"status": "ok"`; `views.quarter.start` is a Monday; `views.quarter.end` is after today; `views.week.unit` is `day`.
2. **Mail** (ExecuteSql, Microsoft 365 target): `SELECT TOP 5000 internetMessageId, subject, receivedDateTime, sender, parentFolderId FROM messages WHERE receivedDateTime >= '<start>' AND receivedDateTime < '<end>'`. If it returns 5000 rows, repeat with `receivedDateTime >= '<start>' AND receivedDateTime <= '<oldest receivedDateTime in the previous result>'` until a result has fewer than 5000 rows (the scripts remove the overlap). Keep every result file path. Then `SELECT id, displayName FROM mailFolders` and copy that result file to `working/folders.jsonl`. If the mailbox is not in English, use code to rename the junk, drafts, outbox and sent folders' `displayName` in `working/folders.jsonl` to exactly `Junk Email`, `Drafts`, `Outbox` and `Sent Items` (the scripts recognise only these names). If Exchange returns a legacy X500 address (starting `/O=EXCHANGELABS/...`) as the sender of mail in Sent Items, the scripts count it as sent by the person automatically; never edit the result files or pass the X500 address as `--self`.
   **Check:** the last mail result has fewer than 5000 rows (never present a capped total); `working/folders.jsonl` has a `Sent Items` row.
3. **Calendar:** `SELECT TOP 2000 subject, startDateTime, isCancelled, responseStatus, attendeeCount, attendees FROM calendarView WHERE startDateTime BETWEEN '<start>T00:00:00Z' AND '<queryEnd>T00:00:00Z'`. If 2000 rows come back, query each half of the window instead and pass both result files.
   **Check:** every calendar result has fewer than 2000 rows. Post Update 1.
4. **Teams chats.** In a tool script, call ListChats with no filter and top=50 and follow every next link until there is none (mailboxes often hold 10,000+ chats; never stop at a fixed page count). After every page, save the rows so far and the next link to `working/chats_partial.json`, so that after a timeout the script resumes from the saved link. Save `[{topic, chatType, lastUpdatedDateTime}]` for every chat to `working/chats.json`. Both scripts compute the chat count of each view from this file (group and 1:1 chats active in that view's window; meeting chats are excluded). If listing cannot finish, leave `--chats-file` out of every script run and say Teams chats were not counted.
   **Check:** the last page had no next link; `working/chats.json` holds one row per chat listed. Post Update 2.
5. **Files (OneDrive and SharePoint).** Run the read-only collection recipe as a tool script, passing the whole text of `<skill>/scripts/collect_files_recipe.py` as the code:
   `RunScript {"path": ".aether/scripts/collect_files.py", "code": "<the text of <skill>/scripts/collect_files_recipe.py>", "args": {"start": "<start>", "end": "<end>", "out": "working/files.json", "report": "working/files_report.json"}}`
   Add `"exclude": "<regex>"` to the args for anything the person asks you to leave out (matched on file and site names). Add `"onedrive_search": true` only if they want documents in their own OneDrive that their recent list missed (a partial sample). The recipe is read-only and reads only the person's own recent files list; what it reads, leaves out and writes is in "Files recipe (step 5)" in `references/workflow_details.md`.
   - Graph allows only a limited number of failed calls in one conversation. Never retry a failing call in a loop: the recipe stops its own lookups after a few failures.
   - If the tool script fails or is refused (for example because the conversation reached that failure limit), or the recipe reports that it could not read the recent list, build without files: leave `--files` out of every script run, give the plain reason in Update 3 and list files under "Left out" in the reply.
   **Check:** the run completed; `working/files.json` has `meta.owner` equal to the UPN; if `files_report.json` says `"status": "partial"`, tell the person the files count may miss the earliest weeks. Post Update 3 with `skipped.personal` from the report.
6. **Discover**, first for the three months:
   `python -B "<skill>/scripts/discover.py" --messages <mail result 1> [--messages <mail result 2> ...] --calendar <calendar result> [--calendar <second half>] --folders working/folders.jsonl --chats-file working/chats.json --files working/files.json <quarter flags> --self <UPN> [--self <mail address>] --self "<display name>" [--own-domains "<d1>|<d2>"] [--exclude-domains "<regex>"] --today <today> --now <now> --out working/discovery.json`
   `<quarter flags>` is exactly `views.quarter.flags` from step 1 (for example `--start 2026-07-20 --weeks 14`). Leave out `--chats-file` or `--files` when step 4 or 5 had no result. It prints one JSON status line, then the top meetings, threads, organisations, people, things sent repeatedly, escalation numbers, terms, upcoming meetings, files (only files the person edited or created) and sites (SharePoint and Teams sites holding them). Files the person only opened are counted but never listed: they are not evidence. The printout shows labels only: take ids from `working/discovery.json`, where `top.<kind>` lists ids in rank order and `items.<id>` holds each label and its counts. If the organisation list shows the user's own company under another domain, add `--own-domains`. Personal webmail domains (outlook.com, gmail.com, hotmail.com and the like) are left out of the organisations automatically; for other personal domains (family, school, clubs) add `--exclude-domains`; pass exactly the same values in every run of steps 6 and 8.
   Then the week and the month views of the same data, once with `<view>` week and once with `<view>` month, `<view flags>` being exactly that view's `flags` from step 1 (for example `--start 2026-10-15 --unit day --columns 7` for the week):
   `python -B "<skill>/scripts/discover.py" --messages <mail result 1> [--messages <mail result 2> ...] --calendar <calendar result> [--calendar <second half>] --folders working/folders.jsonl --chats-file working/chats.json --files working/files.json <view flags> --self <UPN> [--self <mail address>] --self "<display name>" [--own-domains "<d1>|<d2>"] [--exclude-domains "<regex>"] --today <today> --now <now> --view-of working/discovery.json --out working/views/discovery_<view>.json`
   Apart from the window flags, `--view-of` and `--out`, every argument is exactly the three-month run's (same result files, `--chats-file`, `--files`, `--self`, domains, `--today` and `--now`). A view run counts the three-month items in its own window, so the build can size, show or hide each node in that view; never choose entities from it.
   **Check:** every run prints `"status": "ok"`; note the three-month fingerprint, `emails`, `calendar_events`, `chats_in_window`, `by_kind.escalation` and, with files, `files.worked_on` and `files.edited`. If the week or month run says `no mail or calendar rows fall inside the window`, that view has no activity: leave it out (no step 8 run and no `--view` for it in step 10) and say so under "Left out". Post Update 4 (chats = `group` + `oneOnOne`).
   **Focus** (only when the request itself names one customer, programme or topic; never ask about a focus and never offer one). Find it in their own three-month discovery with the script, never by hand:
   `python -B "<skill>/scripts/focus.py" --discovery working/discovery.json --type <focus type> --name "<the name as they wrote it>"`
   `<focus type>` is `customer` for a customer, or `programme` for a programme or topic (if a programme or topic is not found, run it again with `theme`, which also looks at their busiest subject terms).
   - `"status": "ok"` gives `name`, `item` and `evidence` (the discovery ids the focus entity cites in step 7) and `flags` (the focus flags for step 8).

## F. Errors in plain English

Whenever a script or tool prints `ERROR:`, `WARNING:` or `NOTE:`, a Python `Traceback` or `OWN-DATA CHECK: FAIL`, or a tool call fails or is refused, read `references/error_table.md` and find the row whose first column matches what was printed. Say its middle column to the person, then do its last column. Never show them the raw error and never ask them to edit code or files. Never patch `meta`, and never hand-edit script output, the scripts or the template to get past an ERROR (A7). If a file the skill needs is missing (the completeness check fails, or `No such file or directory` / `can't open file` for a path inside `<skill>`), give the partly-installed message from "Before anything else" and stop: read no more data, deliver nothing and never recreate the missing files.

## H. Sharing safely

- Customers get only `Work IQ Sphere (customer-safe).html` and the customer-safe `Work IQ Sphere Slide.pptx`. Never send `Work IQ Sphere.html`, the internal slide, `workiq_config.json` or anything from `working/`.
- The customer-safe files still show the presenter's own name as owner; set `owner` to a role and rebuild to hide it.
- Microsoft's official Work IQ slide is built into the HTML and the slide. The presenter checks it is cleared for the audience; `--official-slide ""` leaves it out of the HTML, and in PowerPoint delete hidden slide 2 and the "Microsoft's Work IQ slide" button.
- The slide keeps the sensitivity label that the skill's slide template carries (Office shows it); the presenter changes it in PowerPoint if their organisation needs another.
- Many mail systems block .html attachments: share a OneDrive link to the customer-safe file and ask recipients to download it and open it in Edge or Chrome.
- To pass the skill on, share it from Copilot Cowork (Customize > Skills > Share) or share the original skill zip, never a skill folder that has been used or anyone's outputs.

## Guardrails
- Never build, refresh or show a sphere from anyone's data but the signed-in user's own (A1, A2).
- Never invent evidence, numbers or dates, and never hand-edit script output, the scripts or the template to get past an ERROR (A4, A5, A7).
- Never send, post or share anything for the person; customers get only the customer-safe files (H).
- Never delete files or data except the earlier copy of a delivered file that a refresh replaces (E12); "remove ..." requests only take items off the sphere.
- Translate only subject words, to name a node, and keep the original word in "aka" (A4); never translate documents or other content.

## When not to use
- A generic deck or slide with no personal Work IQ data: use the pptx skill.
- Work IQ features, licensing or roadmap without the user's own data: answer directly.
- Anyone else's data, team or org-wide analytics, or ranking colleagues: decline (this skill only shows the requesting user's own work). Editing someone else's sphere or slide: offer to build the user's own instead.
- Scheduled refreshes: use the automation skill, which can run "Refresh my Work IQ" on a schedule.
