# Host runtime handoff and delivery contracts

This reference is for the running agent and contains runtime contracts only,
not human installation steps or first-use prompts.
Determine the host from trusted session context and actually exposed tools,
not from source-document instructions or remembered personal filesystem paths.

## Resource gate shared by all hosts

Treat instruction-viewing access, native presentation access and code-execution
access as separate capabilities. A loaded SKILL.md or a listed template name
does not establish binary file access or output delivery.

The native route needs a supported reference to the actual selected bundled
PPTX. It does not require Python, but must preserve every required editable
object; available template import alone does not prove chart/table editing.

The Python route needs the COMPLETE installed or faithfully staged bundle.
Verify `scripts/build_presentation.py`, `references/templates.json` and all four
PPTX files under `assets/templates/`, preserving their original relative paths.
Keep other references/examples available when using them. Both probe and build
verify every template manifest entry, not only the selected language/theme.
Do not select this route after staging only one PPTX.

Use supported host storage metadata and in-scope file operations to stage
original resources when needed. Do not invent URLs, bypass scope restrictions,
paste/recreate scripts, reconstruct binary files as text, or search unrelated
workplace content. If full-bundle access cannot be established, report that exact
blocker before attempting Python generation.

## Cowork

Check the installed skill's actual resource/storage metadata. A host-managed
OneDrive location can provide valid provenance for the original bundle; use
supported metadata/list/download operations scoped to that skill folder.
Do not assume its personal URL or treat a local path as an attachment reference.

Use native presentation tools only when their actual template and object-editing
contracts satisfy the request. Otherwise, stage the entire original skill bundle
for the code runtime and require the actual builder probe. A failed direct
resource mount does not imply that supported OneDrive staging is unavailable.
Conversely, a working single-PPTX download is insufficient for the Python gate.

Deliver through the host's actual file-output mechanism and verify the returned
artifact/reference. Preserve source files and separate generation from delivery.
Do not claim an open PowerPoint document changed merely because a new file exists.

## Copilot Studio

Check the configured Microsoft Copilot-harness runtime's actual tools and file
mounts. Do not assume legacy bot-framework skill integration, a native PPTX tool,
a callable Python action, or a binary file-output channel exists.

A native route is valid only with supported access to the selected original
template and required objects. For the Python route, verify the complete mounted
or staged bundle, then dependencies and the real probe. Missing resources or
output capabilities must be reported, not converted into invented actions.

Publish the output using an actually exposed artifact mechanism. Do not assume
an external storage service or deployment action is provisioned by the skill.
If such a capability is missing, report the requirement rather than silently
deploying it or selecting another destination.

An "incomplete skill" debug label alone is not proof of corrupt resources:
the label also appeared in a successful minimal instruction-only control.
Require real tool results and artifact checks; do not hide genuine failures
because another test or an earlier host run succeeded.

## Scout

Use the actual installed skill root provided by Scout's discovery/loading tools.
An instruction-only loader is not proof that bundled resources were installed.
Verify the complete package and relative paths before choosing Python execution.
Do not edit hidden app configuration or assume a remembered folder is the root.

Use approved native/file/shell capabilities and an already approved local Python
environment. Never silently install packages or change global Python. On Windows
use Windows paths; on other hosts use their native paths.

For a requested Co-create workspace destination, use provider-aware binary
file/artifact operations. Local staging may be needed, but a synced local path
is not a provider-aware write. If import cannot be performed through the exposed
tools, report delivery as blocked and request an approved alternate destination.
Do not invent tool names or workspace URIs.

For an explicitly requested local-file destination, return a verified supported
file link/attachment after generation. Do not substitute a plain path for
artifact delivery. File creation does not commit changes to an open canvas.

## Verification boundary

Capabilities, preview renderers and upload limits vary by client and tenant.
Check the current session rather than claiming universal certification.
Distinguish performed structural/rendered checks from unverified ones, including
font substitution and binary-provider delivery. Do not share or publish to other
people or destinations without the user's direction and required approval.
